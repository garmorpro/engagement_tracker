# Engagement Tracker

Internal tool for tracking client engagements (audits/SOC reports), their timelines, milestones, and team assignments. PHP + vanilla JS/CSS, no frontend framework, no build step.

Live at `https://engagements.morganserver.com` (see `path.php`). Repo: `github.com/garmorpro/engagement_tracker`. Runs on a Raspberry Pi 3 (`ms-webserver-01`) — see "Hosting" below.

## Stack

- **Backend**: Plain PHP (mysqli, prepared statements), no framework
- **Dependencies**: Composer (`vlucas/phpdotenv` for `.env` loading) — but `vendor/` and `composer.json` are **not in this repo**; they live one level above the web root on the server (`/var/www/engagement_tracker/vendor`, next to `.env`). This repo cannot run standalone without that external Composer setup. See "Known issues" below.
- **Frontend**: Vanilla JS (`assets/js/`), plain CSS (`assets/styles/main.css`), no npm/build tooling
- **DB**: MariaDB 10.6 on the Pi (it was MySQL 8 in Docker until 2026-10-27); table names like `service_accounts`, `engagements`, `engagement_timeline`. A MySQL 8 dump needs `utf8mb4_0900_ai_ci` (and `_as_cs`/`_bin`) rewritten to `utf8mb4_unicode_ci`/`utf8mb4_bin` before MariaDB will import it.
- **Auth**: Custom PIN-based login (not password-based) — see Auth section

## Structure

- `index.php` — public login page. Also embeds a super-admin "Admin Dashboard" (account management UI) unlocked via a 6-digit PIN, reachable *before* normal login.
- `auth/` — login, logout, registration, session check, account management endpoints
- `api/` — JSON endpoints for engagement/milestone/team-member CRUD, called via `fetch()` from the frontend
- `pages/` — main authenticated app screens: dashboard (the single engagement list; rows open a side drawer), engagement details, employees, activity log, settings
- `includes/` — shared PHP: `db.php` (connection/env), `functions.php` (helpers + auth guards), `init.php` (an older/partial auth guard used by a few pages), modals
- `path.php` — defines `BASE_URL` (hardcoded to production) and `ROOT_PATH`

## Auth model

- Login is by 4-digit PIN (6-digit for `super_admin`) tied to a `user_id`, not a traditional password. PINs are stored **hashed** (`password_hash()`/`PASSWORD_DEFAULT`) in `service_accounts.passcode` and checked with `password_verify()` in `login.php` and `verify_admin_pin.php`. New/edited PINs are hashed before insert/update in `register.php`/`update_account.php`. The edit-account form no longer prefills the PIN field (hashes aren't reversible) — leaving it blank on edit keeps the existing PIN.
- Two different session guards exist in the codebase: `auth/session_check.php` (full guard: login check + inactivity timeout + DB `logged_in` flag) and `includes/init.php` (lighter guard, used by only 3 pages). New pages should use `auth/session_check.php` for consistency.
- API endpoints (`api/*.php`) use `requireApiAuth()` (defined in `includes/functions.php`) — call it immediately after requiring `functions.php`.
- The super-admin "Admin Dashboard" (view/add/edit/delete accounts, reachable from the public login page via a 6-digit PIN) is gated by `requireAdminVerified()`, which checks a `$_SESSION['admin_verified']` timestamp set by `auth/verify_admin_pin.php` on success (15-minute window). Any endpoint that manages accounts must call this.
- PIN entry (`login.php`, `verify_admin_pin.php`) is rate limited via the `login_attempts` table and the `isRateLimited()`/`recordFailedAttempt()`/`clearAttempts()` helpers in `functions.php`, keyed by IP (and IP+user_id for regular login). See known issues for thresholds and the proxy caveat.
- Every `session_start()` call site must go through `startSecureSession()` in `includes/session_config.php` (never call `session_start()` directly) — it sets `SameSite=Lax`/`Secure`/`HttpOnly` on the session cookie, which has to happen before the session starts.

### Team / Division of Labor (DOL) rework

- **New `employees` table** (`emp_id`, `emp_name`, `emp_role` — one of `manager`/`senior`/`staff`/`intern`) is a lightweight roster used purely for autocomplete when adding someone to an engagement's team. It is **not** foreign-keyed to `engagement_team` — adding a team member still just copies `emp_name`/`role` as free text into `engagement_team`, exactly as before; `employees` only supplies suggestions. Created and seeded (from distinct names already used in `engagement_team`) by `includes/migrate_create_employees_table.php` (CLI-only) — **must be run once on the server** after deploying.
- New endpoints: `api/search-employees.php` (autocomplete search) and `api/add-employee.php` (adds a new person to the roster; idempotent — returns the existing row if the name already exists). Both `requireApiAuth()`.
- DOL (duties, e.g. `CC1, CC2`) is still stored exactly as before — a comma-separated string per audit type (`emp_soc1_dol`, `emp_soc2_dol`, `emp_hipaa_dol`, `emp_hitrust_dol`, `emp_fisma_dol` on `engagement_team`) via the same `api/update-team-member.php` contract. Only the *input UI* changed: a tag input (type a duty, Enter/comma to add, click × or Backspace to remove) instead of a raw text box, joined back into the same comma-separated string on save.
- **"Manage Team Members" is a split workspace** (roster on the left, a detail/editor panel on the right — master/detail, like the dashboard list + drawer itself), replacing the original two-column list-plus-stats layout and the separate "Edit Team Member" popup it used to open. Mocked up first as a Claude Artifact with two flow directions before building — "B: Split Workspace" was the one picked. Selecting a roster row (or hitting "Add Team Member") opens that person's editor in the same right pane: role segmented control, budgeted hours, and the per-audit-type duty tag inputs, all in place — no nested Swal for Edit. Remove asks for confirmation inline in the same pane (a second Swal.fire() while this modal is open would replace the shared popup instance and close the whole thing, the same issue the "add as new employee" role picker already had to work around, so its confirm — and the new-employee role picker's own step — both render inline instead of nesting). While the inline remove confirm is showing the actions row gets `.is-confirming` (the Save group is hidden and the bar owns the row); note that inside any Swal window text may break mid-word unless a container sets `overflow-wrap: normal; word-break: normal`, and flex buttons need `flex-shrink: 0; white-space: nowrap`. Add/Edit/Remove all patch the in-memory roster and re-render in place rather than reloading the page; only closing the whole modal reloads, to refresh the Team card/drawer behind it. Implemented independently in both files under a `team3-` CSS/JS prefix (`team2-` markup/classes from the old layout — chips, tag inputs, segmented control, avatars — are still reused inside the new panel, just recomposed): `openManageTeamModal()` in `pages/dashboard.php`, and the `manageTeamIconBtn` click handler in `pages/engagement-details.php`.
- **Budgeted hours** (`engagement_team.budgeted_hours`, `DECIMAL(6,2)` NULL) — hours a team member is budgeted for on a given engagement. Captured on the Create Engagement wizard's Team step (see below) and editable afterward via "Edit Team Member"; shown as a small badge on the read-only Team card and in "Manage Team Members". Purely informational — not consumed by any calculation. Distinct from the DOL Generator's (`pages/tool/dol-generator.php`) own hours input, which is ad hoc and never persisted, used only to compute that one split. `api/add-team-member.php`/`api/update-team-member.php` both accept/store/return it. Added by `includes/migrate_add_team_budgeted_hours.php` (CLI-only) — **must be run once on the server** after deploying.
- **Duties always display/edit in a fixed canonical order**, never whatever order they were typed in — the DB column itself stays a plain comma-separated string in whatever order, this is purely a display/edit-time sort. SOC 2: the 9 Common Criteria numerically, then `Availability, Confidentiality, Processing Integrity, Privacy` (this exact sub-order — confirmed with Garrett after it first came out reversed, since it disagreed with the DOL Generator's own pre-existing `SOC2_CRITERIA_ORDER`, which is the one that's actually right). SOC 1: numeric by whatever digits are in the tag (`CO1, CO2, ... CO10`, not lexical). Anything else (a stray custom tag, or another audit type like HIPAA/HITRUST/FISMA with no defined canonical order) falls back to alphabetical. Implemented three times, kept in sync by hand since there's no shared PHP/JS module: `sortDolTags()` in `pages/dashboard.php` (JS, both the read-only Team card and the "Manage Team Members" detail panel's tag input, which re-sorts on every render so removing a tag can't leave a stale order), the `$sortDolTags` closure in `pages/engagement-details.php` (PHP, for that page's server-rendered Team card) plus its own separate JS copy for that page's "Manage Team Members" detail panel (JS-rendered, unlike the read-only card), and `sortSoc2Criteria()` in `pages/tool/dol-generator.php` (the original, pre-existing one — the two above were added to match it, not the other way around).

## One engagement per client (changed 2026-10-27, reverses 2026-10-16)

A client engagement is **one line with every audit type on it** (`eng_audit_type` like `SOC 2, PCI`): one ID (`ENG-YYYY-NNN`), one timeline and due date, one team, one notes log, one status. Duties (DOL) stay separate **per audit type** on each team member (`emp_soc1_dol`/`emp_soc2_dol`/… on `engagement_team`), so "who does what for PCI vs SOC 2" is still visible; budgeted hours are a single number per person. A "client" is still not a table, just the `eng_name`.

History, so this isn't flip-flopped again by accident: on 2026-10-16 every audit type was split into its own engagement (the types run on different timelines/teams, PCI especially), and two client-grouping UIs were built and rejected ("I'm seeing duplicates"). On 2026-10-27 Garrett decided he wanted one line per client after all and chose to **merge everything, including PCI**, accepting that all of a client's audit types now share one timeline and due date. Don't re-split or re-add client grouping without asking.

- **Onboard Client** creates ONE engagement however many audit types are ticked (see below).
- **Merging the old split pairs**: `includes/merge_engagements_by_client.php` (CLI; `php includes/merge_engagements_by_client.php [--dry-run] [--only "Client"] [--db NAME]`) is the inverse of the old split script (deleted; it's in git history before 2026-10-27). The lowest ENG id for a client name survives; audit types are joined in order; SOC fields/TSC/scope are filled from a sibling only where blank; the same person's team rows are merged (duties unioned per audit type, hours added), people only on a sibling are moved; the timeline keeps the survivor's and fills blanks; notes, milestones and planning docs move across; the emptied sibling is deleted. A group where two engagements share an audit type is skipped and reported (merge by hand). Always back up the DB first, rehearse on a scratch copy with `--db`, then `--dry-run`, then run it for real. The pairs it was written for are the ones the 2026-10-16 split made: Payabli (019+028), Credit Solutions (026+029), KyxStart/Soliish (027+030), PayEntry (011+031), PCMI - SCS/SEA (020+033), PCMI/PCRS (015+032).
- **Planning docs**: an engagement can have several. `engagements.eng_planning_doc` is a TEXT list, one stored filename per line (`planningDocList()`/`planningDocStore()` in `includes/functions.php`; files live in `uploads/engagement-screenshots/`). `includes/migrate_planning_docs_multiple.php` widened the column from VARCHAR(255) — **must be run once on the server** after deploying. Upload adds to the list; view/delete take a `file`; the drawer lists each doc with View/Remove and an "Add Another" button; Archive & Export includes every doc.
- The top stat cards and "Needs Attention"/"Due Soon" counts are per engagement.

## Clients with several entities (2026-10-28)

Some clients (PCMI: TruComply, SCS/SEA, PCRS) have several separate engagements that each keep their own timeline, dates, team and DOL, but are one client for conversation purposes. The answer is a light link, NOT a merge and NOT a grouped list (rows stay one per engagement, as decided on 2026-10-16/27): `engagements.eng_client` (optional free-text client name, autocompleted from existing ones via `<datalist id="clientNames">`). It is set in the Edit Engagement window and the Onboard Client wizard (Basics step) and is part of the list search text.

- **Drawer:** an engagement whose `eng_client` matches others shows a strip under the onboarding banner ("PCMI · 3 engagements") with a chip per sibling; clicking one calls `switchDrawerTo()` for that entity (fades the current engagement out while the next loads, then its header and sections rise in with a stagger via `playDrawerEntrance()`, which opening from the list also uses; `prefers-reduced-motion` turns it off). `getEngagementSiblings()` (non-archived only) feeds `siblings` in `api/get-engagement-details.php`. No siblings, no strip.
- **Shared notes:** `engagement_notes.note_scope` is `engagement` (default) or `client`. A `client` note logged on any engagement of the client shows in the Notes & Meetings log of every one (`getEngagementNotes()`, tagged "All PCMI · from <entity>" when it came from another engagement). Each of the four note windows gets a "Who should see this?" switch (`renderMeetingScope()`), only when there are siblings; default is the whole client for Weekly Status and Note, this engagement only for Planning and Client Planning (those mark THIS engagement's own timeline, even if shared). `api/add-engagement-note.php` falls back to `engagement` if the engagement has no client.
- **Archive & Export** includes the shared notes (tagged); **removing** an engagement hands its client-wide notes to a remaining non-archived sibling (lowest ENG id) instead of deleting them, so the rest of the client keeps them. Notes marked `engagement` go with it, as before.
- Added by `includes/migrate_add_client_grouping.php` (**must be run once on the server**); every read/write that uses the new columns falls back gracefully before then. Existing notes stay `engagement` until changed (e.g. `UPDATE engagement_notes SET note_scope='client' WHERE note_type='weekly' AND engagement_idno IN (...)`).

- **Duplicating an engagement**: `php includes/duplicate_engagement.php ENG-2026-015 "New name" [--no-team] [--no-timeline] [--client "X"] [--status planning] [--dry-run]` (CLI) makes a new engagement with a fresh ENG id from an existing one: details, client, team (duties/hours, not independence) and timeline dates (not completed ticks). Notes, planning docs, checklist ticks and milestones are not copied. Copies columns generically via `SHOW COLUMNS`, so new columns follow automatically.

## PCI checklist (2026-10-27)

Garrett's PCI tracking sheet, as a fixed checklist: 5 phases, 12 steps (`PCI_CHECKLIST` in `includes/functions.php`; Phase 0 Planning & Kick-Off: Internal Planning Call, Kick-Off Call, Send IRL; Phase 1 Fieldwork: Create Draft ROC, Fieldwork; Phase 2 Documentation: Document ROC, QA ROC, Deliver Draft ROC; Phase 3 Report Finalization & Delivery: Create Final ROC, QA Final ROC, Deliver Final ROC; Phase 4 Project Closeout: Reconcile Zoho). Ticking a step records the date it was completed (server time, shown next to it); unticking removes it; re-ticking keeps the original date. Plain checkboxes: no per-step due dates.

`pciChecklistMode($eng)` (PHP; `pciChecklistMode(eng)` in the dashboard JS mirrors it) decides what an engagement shows:
- **`only`** (PCI is its only audit type): the checklist REPLACES the Timeline & Key Dates section in the drawer (no Import/Edit Timeline; the planning docs row and Weekly Status Call stay). The list row's Due column shows "N of 12 steps" instead of a date and becomes **Archive Ready** once `deliver_final_roc` is ticked (`PCI_CHECKLIST_FINAL_STEP`, handled in `getDueInfo()`). Needs Attention: a ticked step counts as "filled out" (the old PCI carve-out — timeline OR planning doc — now reads checklist progress OR planning doc).
- **`off`** (PCI plus other types): the normal timeline, plus an "Add PCI checklist" button at the bottom of the timeline section. **`on`** (after pressing it): the timeline AND a "PCI Checklist" section with a Remove button (hides it; ticked steps are kept). `engagements.eng_pci_checklist` (0/1) holds this; `api/set-pci-checklist.php`.
- **`none`** (no PCI): nothing about the checklist appears.

**ROC delivery date** (`engagements.eng_roc_delivery_date`, a DATE): a date picker appears whenever PCI is a ticked audit type, in the Onboard Client wizard (Audit Scope step) and in the Edit Engagement window; unticking PCI clears it. It is saved by its own guarded UPDATE after the main create/update (`api/create-engagement.php`, `api/update-engagement.php`), so a server that hasn't run the migration can still save everything else. For a PCI-only engagement it IS the due date: `getDueInfo()` classifies it overdue / soon (within 5 days) / ok exactly like the SOC final-report date until `deliver_final_roc` is ticked, the list row shows it with "N of 12 steps" under it, and `getDueItemsSummary()` lists "ROC Delivery" in the What's Due popup (only where the checklist is in use). On a combined engagement it is informational (drawer Details, above the checklist when added, and the PDF). The full details page (`engagement-details.php`) has no field for it.

Storage: `engagement_checklist` (one row per ticked step; `api/update-checklist-step.php`), created with the `eng_pci_checklist` column by `includes/migrate_create_engagement_checklist_table.php` — **must be run once on the server**. The drawer data (`api/get-engagement-details.php`) includes `checklist`; `getChecklistMap()`/`getAllChecklistData()` return `[]` if the table doesn't exist yet, so deploying before migrating is safe. Archive & Export puts the checklist in the PDF (replacing the Timeline section for `only`, in addition to it for `on`), removal and the merge script carry/delete its rows. Only the dashboard drawer was updated: `engagement-details.php` (the full page) still shows the SOC timeline.

## Onboarding completeness ("Needs Attention")

Dashboard-wide check for whether an engagement's setup is actually done, separate from the date-driven "Due Soon" filter (overdue/due-soon/archive-ready). Implemented twice in lockstep — `getSetupInfo()` (PHP, `pages/dashboard.php`) for the initial list-row render, and `drawerSetupStatus()` (JS, same file) for the drawer banner once it already has the team/timeline data client-side — keep both in sync when this logic changes.

Checks, in the order they'd naturally get done:

- **Team** — at least one `engagement_team` row.
- **Timeline** — an `engagement_timeline` row exists AND at least one date column is actually set (no row at all, or a row with every date still blank, both count as not filled out).
- **Planning doc** — `eng_planning_doc` is set.
- **DOL** — (only raised `DOL_GRACE_DAYS` = 2 days after the internal planning call happened: its completed tick if set, else its scheduled date; with no call on the timeline it isn't raised at all. DOL gets assigned in that call. Mirrored in `getSetupInfo()` and `drawerSetupStatus()`.) Every audit type on the engagement that actually has a DOL column (`SOC 1`/`SOC 2`/`HIPAA`/`HITRUST`/`FISMA` — see `DOL_AUDIT_TYPE_COLUMNS`) has DOL assigned to at least one team member. PCI and ISO have no DOL column at all, so an engagement with only those types is never flagged for missing DOL.
- **PCI-only carve-out**: an engagement whose only audit type is PCI is tracked less formally in practice — per Garrett, some are tracked with a filled timeline, others with just a planning doc — so neither is independently required; it's flagged only if it has NEITHER. Scoped to PCI specifically, not extended to ISO even though ISO shares PCI's no-DOL-column treatment above.

Surfaced in three places: the "Needs Attention" stat card + toolbar filter (amber, independent from the red "Due Soon" filter — a row shows if it matches either when both are active), a compact flag on each list row (first missing item only), and a banner at the top of the drawer listing everything missing.

## Onboard Client wizard

`pages/dashboard.php`'s "Onboard Client" button opens a 4-step wizard (`.eng-wizard-*`) that makes **one** engagement through a single `api/create-engagement.php` call (audit types joined as `SOC 2, PCI`), then a batch of `api/add-employee.php`/`api/add-team-member.php` calls once it exists:

1. **Basics** — name (required), location, POC, Manager (roster autocomplete via `search-employees.php`, falling back to `add-employee.php` for a brand-new name), status.
2. **Audit Scope** — audit types (tick every one that applies; they all go on the same engagement), SOC type/dates (sent only when SOC 1 or SOC 2 is ticked, or nothing is), TSC (only with SOC 2, or nothing ticked), scope.
3. **Team** — roster autocomplete, for adding any number of Senior/Staff/Intern members, each with one budgeted-hours box. Blank hours saves `budgeted_hours = NULL` (on the engagement, nothing budgeted — no hours badge on the Team card); a typed 0 saves 0 and shows "0 hrs". Manager is filtered out of this step's search results and new-employee role choices — that role stays the dedicated Step 1 field. Optional; people can always be added later from the Team card, where duties (DOL) are set per audit type.
4. **Review** — summary of everything above, plus Repeat/Notes, then submits.

Brand-new roster names are created first (idempotent `add-employee.php`, once per name), then the Manager and every member go through `add-team-member.php` in parallel via `Promise.allSettled`. If any of those secondary calls fail the engagement itself still exists, so that's reported rather than treated as a failed onboarding.

**After submit the wizard turns into a summary** (`showOnboardSummary()`, the `data-panel="done"` panel — deliberately not counted in `TOTAL_STEPS`): "Client onboarded", the client name, the engagement (audit-type badges, ID, status, an Open link that reloads straight into its drawer, and who's on it) and a reminder to add the planning doc and timeline from the drawer. Team assignments that didn't save are shown inline ("N of M … add them from the Team card"). If the create itself fails nothing was made, so it's a normal error with the wizard still open. Done / × / Cancel / Esc / clicking the backdrop all reload once the summary is showing.

A freshly onboarded engagement shows "No planning doc" under Needs Attention until one is uploaded.

## Notes & Meetings

Replaces two things that used to live directly on the drawer: the single `engagements.eng_notes` text field (one field, silently overwritten every edit, no author/timestamp) and the per-person independence popup (`api/update-team-independence.php`, one SweetAlert2 at a time, no notes attached — that endpoint still exists but the drawer no longer calls it). Mocked up first as a Claude Artifact before building, per Garrett.

A running, timestamped log in a new `engagement_notes` table (`includes/migrate_create_engagement_notes_table.php` — **must be run once on the server**), fed by four buttons in the drawer's "Notes & Meetings" section (`.mtg-*` in `pages/dashboard.php`; `wireMeetingButtons()` re-wires them from `renderDrawer()` on every render, since `drawerBody`'s innerHTML — the buttons included — is fully torn down and rebuilt each time the drawer refreshes):

- **Planning Meeting** — notes, plus independence for every team member inline in the same modal (a segmented Yes/No/— per person, seeded from `engagement_team.emp_independent`) instead of a separate popup per person. Marks Internal Planning Call complete on the timeline.
- **Client Planning** — notes only. Marks Client Planning Call complete on the timeline.
- **Weekly Status** — notes only. Doesn't touch the timeline (distinct from the existing weekly-status-call *day-of-week scheduling* feature already on the timeline section, which this doesn't change).
- **Note** — notes only, for anything else.

All four post to `api/add-engagement-note.php`, one transaction rather than chained client-side calls so a "log this meeting" action can't end up half-saved: insert the `engagement_notes` row; for Planning only, write each person's independence answer through to `engagement_team.emp_independent` (the live value the Team card's now-read-only badge reads — `independenceIconHtml()` lost its click handler and `openIndependenceMenu()` was deleted) *and* capture the same answers as an `independence_snapshot` JSON column on the note itself (what was confirmed *at that meeting*, which stays fixed even as the live answer keeps changing after); for Planning/Client, mark the matching `engagement_timeline` `*_completed_at` column complete the same way the timeline's own click-to-complete checkbox does. Saving always calls `refreshDrawer()` rather than patching the DOM in place, so the log, the Team card's independence badges, and the timeline's checkmarks all land in sync from one re-fetch.

`getSetupInfo()`'s timeline/DOL checks (see "Onboarding completeness" above) look at the timeline's *date* columns, not its `*_completed_at` columns — logging a Planning/Client note doesn't by itself satisfy "Needs Attention" unless a due date was also entered separately. That's intentional: "filled out" and "step completed" are different questions.

Any pre-existing `eng_notes` content isn't migrated automatically (no reliable author/timestamp to attribute it to) — the drawer shows it read-only in a "From before this log existed" callout above the log instead of silently dropping it.

## Archive & Export (2026-10-27)

There is no archived state to browse. Clicking **Archive & Export** (row action, drawer button, or the details page) runs a two-step flow from `archiveEngagement()` in `pages/dashboard.php` and `pages/engagement-details.php` (each page has its own copy of the JS):

1. `api/export-engagement.php` builds a ZIP and streams it to the browser, named `<ENG-ID> - <client> - <audit type>`, containing **`Engagement Synopsis.pdf`** (details & scope, team with duties/hours, timeline with on-time/late, milestones, the full notes & meetings log) and every planning doc image (`Planning doc.png`, or `Planning doc 1.png`, `2`, … when there are several). Nothing is kept on the server, and the export itself changes nothing.
2. Only after the download is in hand, a second dialog asks "Remove from tracker" or "Keep it for now". Removing calls `api/delete-engagement.php`, which uses `exportRemoveEngagement()`: deletes the notes log, timeline, milestones, team and engagement rows in one transaction, then the planning doc file. (The old delete left the notes and the file behind, and since `eng_idno` comes from `MAX()+1`, a reused number could inherit orphaned notes.) "Delete" (trash icon) goes through the same cleanup.

Code: `includes/engagement_export.php` (data load, PDF, ZIP, removal), FPDF 1.86 in `includes/lib/` (core Helvetica fonts only; text is converted to Windows-1252, so emoji are dropped). PDF decisions made with Garrett: no independence anywhere in it (neither a column nor the planning-meeting snapshot line), duties show the audit type in bold with the CC/CO items regular, canonical duty order. Download only: no History page, nothing stored on the Pi.

For engagements archived before this existed, `includes/export_archived_engagements.php OUTDIR [--remove] [ENG-...]` (CLI, run as `garrett` on the Pi) writes the same ZIPs; with `--remove` it deletes an engagement only after re-opening its ZIP and finding the PDF inside. Rows still marked `eng_status = 'archived'` are filtered out of every list (`dashboard.php`, `functions.php`) until removed; once none are left those filters are dead but harmless. The timeline's own "Archive" step/date and the "Archive Ready" flag are unrelated and unchanged.

## Known issues / backlog

Found during a 2026-07-13 security review — see conversation history for full detail. Fixed same day unless noted:

- **[Fixed]** No auth was actually enforced anywhere: `session_check.php`'s body and its call sites were commented out, and all 16 `api/*.php` endpoints had zero session checks. Restored `session_check.php`, added `requireApiAuth()` to all API endpoints, added guards to `dashboard.php`, `engagement-details.php`, mobile pages, and `pages/tool/work-balance-tool.php`.
- **[Fixed]** `auth/get_account_details.php` returned any user's plaintext PIN given just their `user_id`, no auth required (full credential disclosure via ID enumeration). `auth/update_account.php` let anyone overwrite any account's name/email/PIN. `auth/register.php` let anyone self-register a new `admin`-role account. `auth/get_accounts.php`/`delete_account.php` had no auth either. All five now require `requireAdminVerified()`.
- **[Fixed, then removed 2026-10-27]** Dev/debug and cron/test scripts under `pages/` were reachable over plain HTTP by anyone; they were restricted to CLI, and later deleted outright (see "Slimmed down").
- **[Fixed]** `pages/engagement-list.php`, `engagement-analytics.php`, and `engagement-timeline.php` each had a stray unconditional `logoutUser($conn);` call right after their includes — since `logoutUser()` always destroys the session and redirects, every visit to these pages immediately logged the user out. Removed the stray calls.
- **[Fixed]** PINs were stored in plaintext and compared with `===`. Now hashed with `password_hash()`/verified with `password_verify()` in `login.php`, `verify_admin_pin.php`, `register.php`, `update_account.php`. `get_account_details.php` no longer returns the passcode at all. One-time migration at `includes/migrate_hash_passcodes.php` (CLI-only) widens the `passcode` column to `VARCHAR(255)` and hashes any existing plaintext PINs — **must be run once on the server** (`php includes/migrate_hash_passcodes.php` from the project root) after pulling this change, or existing accounts won't be able to log in.
- **[Fixed]** No rate limiting existed on PIN entry. Added a `login_attempts` table plus `isRateLimited()`/`recordFailedAttempt()`/`clearAttempts()` helpers in `includes/functions.php`. `login.php` caps at 5 failures per 15 min per (IP + user_id) and 20 per 15 min per IP overall; `verify_admin_pin.php` (6-digit super-admin PIN) caps at 5 failures per 15 min per IP. One-time migration at `includes/migrate_create_login_attempts_table.php` (CLI-only) creates the table — **must be run once on the server** (`php includes/migrate_create_login_attempts_table.php`) after pulling this change.
- **[Fixed]** `getClientIp()` originally used `$_SERVER['REMOTE_ADDR']` directly, but this server sits behind a local reverse proxy, so every request showed up as `::1` (loopback) — meaning the rate limiter above would have bucketed every real visitor together under one identifier, letting one person's mistyped PIN lock out the whole team. `getClientIp()` now reads `X-Forwarded-For`/`X-Real-IP`, but only trusts those headers when the direct connection is from a loopback address (otherwise any client could spoof them to dodge rate limits). Confirmed empirically: a real remote login attempt logged `identifier = ::1` in `login_attempts` before this fix. **Verify after deploying** by triggering a failed login from a real remote browser and checking that `login_attempts.identifier` shows an actual public IP, not `::1`/`unknown` — if it's still wrong, the proxy isn't setting either header and needs a different one checked.
- **[Partially fixed] CSRF.** No request had any CSRF protection — the app relied entirely on the browser/PHP session-cookie defaults, with no explicit `SameSite` attribute set at all. Full token-based CSRF protection would need to touch ~48 `fetch()` call sites across 9 files, 6 `<form>`s, and ~20 backend endpoints — deliberately deferred as disproportionate risk/effort for this app. Instead, every `session_start()` call site now goes through `startSecureSession()` (`includes/session_config.php`), which sets `SameSite=Lax`, `Secure`, and `HttpOnly` on the session cookie. This blocks the cross-site POST/fetch requests that CSRF actually exploits, at far lower risk than a full token system, but is not a complete replacement for one — full tokens are still the more thorough option if ever revisited. Requires HTTPS (the `Secure` flag depends on it); this site is HTTPS-only already, so no impact expected, but verify login still works after deploying.
- **[Fixed]** `pages/dashboard.php.bak` and `pages/engagement-details.php.bak` were committed backup files with old, superseded logic — deleted (still recoverable from git history if ever needed).
- **[Fixed]** `display_errors` was hardcoded on in `db.php`, leaking PHP stack traces/file paths to any visitor who triggered an error. Now off by default; only enabled when `.env` sets `APP_DEBUG=true`. Added `.env.example` documenting the required (`DB_HOST`/`DB_USER`/`DB_PASSWORD`/`DB_NAME`) and optional (`APP_DEBUG`) variables, since none existed before.
- **Still fragile — `vendor/autoload.php` resolution.** `includes/db.php` walks 3 directories up from `includes/` to find `vendor/`, meaning this repo depends on a Composer setup that lives entirely outside the repo (no `composer.json`/`composer.lock` tracked here, so a fresh clone can't `composer install` on its own). Left the resolution logic itself unchanged since it works in the current production layout and I can't verify a change against the live server topology, but improved the failure path: it now logs the attempted path via `error_log()` instead of dying with a raw filesystem-path message shown to visitors. If this repo is ever deployed somewhere with a different directory depth, this is where it'll break.
- **[Partially fixed] `BASE_URL`.** `path.php` now checks `getenv('BASE_URL')` before falling back to the hardcoded production URL, and `.env.example` documents it. Kept deliberately simple: it uses `getenv()`, not Dotenv directly, so it only works if something earlier in the same request already loaded `.env` (Dotenv calls `putenv()`, which is what makes `getenv()` see it) — not guaranteed on every code path, since `path.php` is sometimes required before `functions.php`/`db.php`. Good enough for the stated goal (an escape hatch for local/staging), not a guaranteed override on every request. Leave `BASE_URL` unset in production `.env` — the hardcoded fallback is correct there.
- **[Fixed] Docker (retired 2026-10-27) had no php.ini — and the lesson still applies** (`php:8.1-apache`, `output_buffering=0`, `display_errors=1`), unlike the old shared host. A bare `ob_clean()` with no active buffer raises a Notice; because `api/create-engagement.php` and `api/delete-engagement.php` called it as their first line, the notice was sent *before* `session_start()`, so the session never loaded and every request returned "Not authenticated" even when logged in — Add and Delete Engagement both silently failed. Guarded with `if (ob_get_level() > 0)` in those two files and `includes/save_dol.php`. Watch for the same class of bug: any PHP notice/warning emitted before `startSecureSession()` breaks login state in this environment. On the Pi's default PHP-FPM config `display_errors` is off, but keep the habit.
- **Git history** is uninformative — nearly every commit message before this review was just "update".
- No automated tests exist.

## Conventions

- API endpoints return JSON: `{"success": bool, "message"/"error": string, ...}`. Use `http_response_code()` for non-200 cases.
- All DB queries use mysqli prepared statements (`bind_param`) — keep doing this, no raw string interpolation into SQL has been found in the codebase.
- New pages that require login should `require_once '../auth/session_check.php';` right after `path.php`/`functions.php`. New API endpoints should call `requireApiAuth();` right after requiring `functions.php`.
